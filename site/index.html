Fast-start CI runners for GitHub Actions

A patch series for the official runner that removes two network round trips from the start of every job, plus a container image and a scale-from-zero controller built from it.

Measured, not asserted

Same host, same job, three runs per variant, timed by the runner's own performance counters.

Job assigned to first stepBaselineWith the patch
Median1731 ms1470 ms
Maximum2460 ms1559 ms

The median gain is 15 percent. The worst case falls by 37 percent, because a lock renewal whose latency was on the critical path no longer blocks dispatch. Full method and raw data in docs/performance.md.

What it changes

Dispatch before renewal

The worker starts immediately instead of waiting for an HTTP round trip to GitHub. A failed renewal still stops the worker before any step is reported.

Acknowledge in parallel

The acknowledgement is best-effort by design but used to block the job fetch. It now overlaps it, removing the round trip from the critical path.

Scale from zero

A controller watches queued jobs, mints a single-use configuration for each, and starts one container. Nothing runs when nothing is queued.

Install

docker pull ghcr.io/daniel-gillis/runlet-runner:0.1.0

gh api -X POST repos/OWNER/REPO/actions/runners/generate-jitconfig \
  -f name=runlet-$(date +%s) -F runner_group_id=1 \
  -f 'labels[]=runlet-runner' -f work_folder=_work \
  | jq -r .encoded_jit_config > /tmp/jit.txt

docker run --rm -e RUNNER_JIT_CONFIG="$(cat /tmp/jit.txt)" \
  ghcr.io/daniel-gillis/runlet-runner:0.1.0

A JIT configuration's labels replace the defaults, so the workflow must use runs-on: [runlet-runner] rather than including self-hosted. See the setup guide for the controller, warm pools, and verification.

What it does not fix

  • Queue time at GitHub. About three seconds pass before a runner is told about a job.
  • The job fetch. Roughly 700 ms of GitHub latency remains on the critical path.
  • One job per container. JIT runners are single-use by GitHub's design.
  • Linux only. The image targets linux/amd64 and linux/arm64.
